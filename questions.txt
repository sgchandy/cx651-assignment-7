(1) This implementation uses UDP, which does not guarantee that messages will be delivered. We also don’t have timeouts or retries, so a lost message could leave clients waiting forever. If a create or join request is lost, the client keeps waiting for a response. If a move request is lost, the game does not update, and both players could end up waiting forever. Similarly, if a message from the server is lost, a player may not know the game has started or that it is their turn. If a player misses their own move update, the game can still continue when the opponent plays, unless it was the winning move. UDP can also send duplicate or out-of-order messages, which could cause problems. To fix this, we could add timeouts, retries, and acknowledgements to confirm messages are received. We could also use sequence numbers to identify duplicate messages.

(2) This save/load implementation works if the server crashes and restarts on the same machine while the clients are still running. However, there are some limitations. If the server crashes while saving, the file could be incomplete, causing the load to fail. Since the server loads games in order, one bad file could prevent other games from loading. We also save the C struct directly, which could cause problems if the struct changes or the program runs on a different system. Old save files are not deleted, so completed games might be loaded again. Saving every move to disk could slow down the server when many games are running. Finally, since everything is saved on one disk without a backup, a disk failure could cause us to lose all saved games.
